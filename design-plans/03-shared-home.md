# Один общий дом для двух мобильных web app без ручного обновления

Written against: `d35c7ec881eb3d5d0610c37434aeda5d3f30d1df`

Implementation status: реализовано локально; серверная миграция `20261027190242_shared_home.sql` применена. Проверены UI и две мобильные сессии без reload. Реализация включена в релиз общего дома.

## Evidence chain

- Surface: домашняя вкладка `/calendar-duo/` → `App` → `Apartment` → растения, декор, повреждения, ремонт.
- Problem: пользователь прямо требует синхронизацию этих данных между двумя пользователями установленного мобильного web app, где нет кнопки обновления страницы.
- Design evidence: `Apartment.tsx:10,23–30` читает и пишет локальный снимок через `HOME_KEY`; `Apartment.tsx:70–73` создаёт пакости независимо в каждом браузере. `roomLife.ts:83` определяет общий для устройства `ustime.home.v2`. `App.tsx:7` уже обновляет серверные данные каждые 8 секунд и при возвращении во вкладку, но `api.ts:20` и `types/index.ts` не включают состояние дома. `public/sw.js` не кэширует приватные API-ответы.
- Owner: `src/lib/api.ts`, `src/types/index.ts`, `src/App.tsx`, `src/components/Apartment.tsx`, `HomeWorkshop.tsx`, `PlantNursery.tsx`, `src/lib/roomLife.ts`, новые миграция и SQL-тесты в `supabase/`.
- Scope and affected surfaces: общий дом двух закреплённых профилей, обе мобильные сессии, восстановление после сна/сети. Demo на входе должно оставаться изолированным.
- Uncertainty: актуальные серверные таблицы и политики необходимо проверить перед реализацией миграции. В этом read-only аудите сервер не опрашивался. В опубликованной версии существуют независимые локальные сохранения; автоматическое разрешение конфликтов миграции нельзя выдавать за известное продуктовое правило.

Это явно выбранная функциональная доработка. Она не является визуальной находкой `improve-ui`.

## Design decision

Сервер хранит единственное подтверждённое состояние общего дома. Клиенты отправляют отдельные именованные операции с уникальным ID, а не перезаписывают весь JSON-снимок. Чтение обновляется автоматически через существующий интервал 8 секунд и события возвращения приложения. Локальны только навигация, выбранный персонаж, движения, реплики, открытые панели и черновик имени.

## Reuse

- `api.request` из `src/lib/api.ts` уже обеспечивает refresh токена и ошибки; `App.refresh` и интервал 8 секунд — существующий путь обновления данных. Не добавлять второй бесконтрольный polling-цикл в Canvas.
- `private.member()` и два закреплённых профиля из `supabase/migrations/20261026174744_initial.sql` — действующая модель доступа.
- `private.respond_meeting` в той же миграции — пример атомарного изменения с блокировкой строки; `public`-обёртка работает как invoker, привилегированная реализация находится в `private`.
- `createPlant`, `plantCapacity`, `seeds`, `catalog`, `growPlants` описывают существующие правила, которые сервер должен проверять. Клиентская реализация остаётся для отображения и тестов, а не для доверенной авторизации.
- Новые `src/lib/home.ts` и `src/lib/home.test.ts` изолируют транспорт операций и применение ревизий от Canvas. Общая доменная модель размещается рядом с `roomLife.ts` либо в `src/types/index.ts`; не дублировать типы по компонентам.

## Changes

1. Новая миграция в `supabase/migrations/`
   - Change: добавить состояние дома с ревизией и временем изменения, отдельный журнал ID выполненных операций, а также серверный срок следующей кошачьей пакости. В проекте одна закреплённая пара; не вводить несвязанный multi-tenant продукт. Таблицы и функции защитить существующей проверкой участника; пользователь не получает право записывать произвольный полный снимок.
   - Change: атомарные действия «посадить», «поставить/убрать конкретный предмет», «починить конкретное повреждение». Под блокировкой строки проверять актуальную ревизию/цель, открытие комнаты, количество завершённых встреч, лимит сада, имя и вид. Повторный `operation_id` возвращает прежний результат без второго растения. Декор передаёт желаемое состояние placed/unplaced, а не переключатель toggle, который повторный запрос способен обратить.
   - Preserve: один шаг роста за новую завершённую встречу; старые встречи не выращивают новое растение задним числом. Доверенные ID завершённых встреч и baseline при посадке вычисляет сервер.
   - Verify: две посадки за последнее место не создают переполнение; починка одного повреждения не стирает появившееся позднее другое повреждение; действия в разных комнатах не теряются.
2. Серверное управление пакостями
   - Change: один общий срок и атомарное создание повреждения; оба открытых приложения не генерируют две независимые пакости. Приоритет — сохранить прежнее правило «во время отсутствия не копим повреждения»: запрос активного клиента может атомарно обработать наступивший срок, второй запрос увидит уже новую ревизию. Передавать последнюю посещённую доступную комнату как локальный контекст события, проверяя её на сервере. Закрытый предпросмотр не считается активной доступной комнатой.
   - Preserve: скверный характер, видимые повреждения и возможность ремонта. Сами перемещения кошки и людей не нужно синхронизировать по кадрам.
   - Verify: одновременные запросы двух телефонов дают одно событие и одинаковое повреждение/счётчик у обоих. После долгого закрытия нет пачки накопленных пакостей.
3. `api.ts`, `types/index.ts`, `App.tsx`, новый `home.ts`
   - Change: включить серверный дом в чтение для авторизованной пары; восстановление сессии выполняется существующим `api.request`. Во время видимой страницы обновлять в существующем цикле 8 секунд. Добавить обновление при `online` и `pageshow`, сохранить `focus`/`visibilitychange`. После операции сразу применить возвращённую сервером ревизию; для второго пользователя она приходит при автоматическом чтении. Ответ с меньшей ревизией никогда не откатывает более новый.
   - Change: сериализовать локальные операции либо учитывать их ID при повторной доставке. При обрыве сети не подтверждать сохранение. Сохранить черновик имени, показывать состояние «Нет связи»/«Сохраняем», повторять ту же операцию с тем же ID, если неизвестно, успел ли сервер её выполнить.
   - Preserve: отсутствие приватных API в service-worker cache; никаких `location.reload()` для синхронизации и никаких ручных действий с кнопкой обновления.
   - Verify: активный второй клиент видит изменение не позднее следующего успешного 8-секундного обновления; после возвращения из фона сразу начинается чтение без ожидания интервала. Отсутствие сети не вызывает ложного подтверждения.
4. `Apartment.tsx`, `HomeWorkshop.tsx`, `PlantNursery.tsx`
   - Change: заменить локальные мутации общего состояния подтверждёнными операциями; передавать новые снимки в `worldRef`, выставлять `dirty`, пересчитывать панели, открытия и рост. Удалить независимую генерацию повреждений из animation loop. `saveHome()` больше не является источником истины для общего дома.
   - Preserve: выбранную комнату на каждом устройстве, выбранного персонажа, открытый каталог и введённое имя при приходе серверного обновления. Demo не обращается к приватному дому и не выполняет серверных операций.
   - Verify: посадка, декор и ремонт видны на обеих страницах без reload; кадры Canvas и показания меню соответствуют одной ревизии.
5. Перенос `ustime.home.v1/v2`
   - Change: сохранить старое содержимое до подтверждённого переноса. Импортировать по отдельной идемпотентной серверной операции; не разрешать старому снимку перезаписывать уже существующий общий дом, восстанавливать починенные поломки или подделывать встречи. Разные растения сохранять по ID; при превышении текущей ёмкости показать выбор для переноса и удержать неперенесённые данные локально. Не удалять имена молча. Старые растения до открытия оранжереи сохранить как существующие данные за блокировкой, но не разрешать создавать новые.
   - Verify: повторный запуск и импорт со второго телефона не дублируют ранее принятые сущности; canonical-дом не откатывается.

## Scope

- Inherit: растения/имена/рост, расстановка по комнатам, повреждения, починки и общий счётчик пакостей.
- Verify: одновременные действия, фон iOS/Android, восстановление сети/токена, выход/вход, demo, данные старого браузера.
- Exclude: синхронизацию координат в каждом кадре, принудительный перенос второго пользователя в выбранную первым комнату, новый способ отправки push, изменение календаря или существующих напоминаний. Автообновление состояния дома не равно принудительной перезагрузке версии приложения.

## Validation

- Product: две изолированные browser context с разными пользователями и общим mock-сервером, затем две реальные тестовые сессии на отдельной тестовой базе. Не использовать production-встречи как фикстуры.
- Interface: телефон A сажает именованный кактус в открытой оранжерее → B видит его и тот же рост; B ставит декор → A видит; одно общее повреждение → A чинит → B видит восстановление. Все проверки выполняются без `page.reload()`.
- Lifecycle: B находится в фоне при изменении, возвращается, получает свежую ревизию; сеть пропала при ответе на посадку, повтор с тем же ID не создаёт дубль; черновик имени и выбранная комната не пропадают.
- System: негативные SQL-проверки для anon/постороннего пользователя и поддельного completedCount; серверная валидация закрытой оранжереи; конкурентные операции с последним свободным местом и ремонтом. Доставлять более старый ответ после нового и проверять отсутствие отката.
- Repository: `npm test` и `npm run build` → успех. Добавить `e2e/shared-home.spec.ts`, команда `npx playwright test e2e/shared-home.spec.ts` → успешные двухклиентские сценарии. Создать `supabase/tests/home.sql`; выполнять на изолированной базе: `psql "$USTIME_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/home.sql` → успех и rollback фикстур. На этапе реализации применять актуальный навык Supabase, проверить реальные политики/документацию и выполнить advisors.

## Stop conditions

- Если действующая серверная модель отличается от двух закреплённых участников, уточнить владельца общего дома до создания миграции.
- Не выпускать UI со словами «общий дом», пока двусторонние сценарии без reload не пройдут.
- Если перенос требует молча удалить или заменить чужие растения/ремонт/декор, сохранить исходные данные и запросить выбор только для конкретного конфликта.
