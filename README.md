# UsTime

Наше маленькое место для больших планов на двоих. React + TypeScript + Vite, Canvas, Supabase Auth/Postgres/Storage; GitHub Pages.

## Запуск

Node 22+, npm. Скопируйте `.env.example` в `.env.local`, укажите URL и **publishable** key проекта. Эти два значения публичные; пароли и service-role key в Vite передавать нельзя.

```
npm ci
npm run dev
npm test
npm run build
npm run preview
npm run e2e
```

В текущей ограниченной среде зависимости предварительно доступны локально. `scripts/launch.sh` создаёт npm lockfile при первой установке, проверяет тесты/сборку, создаёт `palp1ix/calendar-duo`, устанавливает публичные repository variables, включает Pages Actions, публикует main и запускает локальный сервер. Запускать из обычного терминала:

```
cd /Users/palp1ix/Projects/calendar-duo
./scripts/launch.sh
```

Production URL после успешного Actions: https://palp1ix.github.io/calendar-duo/ . Не считать сайт опубликованным, пока deploy job не завершён и URL не проверен.

## Два постоянных аккаунта

В этом проекте уже созданы две постоянные учётные записи: `me@ustime.invalid` и `her@ustime.invalid`. Это внутренние идентификаторы, не почтовые ящики. Вход кнопками «Это я» / «Это она» + отдельный пароль. Письма не нужны. Начальные случайные пароли находятся **только** в `.accounts.local.json` (игнорируется Git, права 0600). Передайте второй пароль лично. Пароль можно сменить в настройках. Сохраните их в менеджере паролей: восстановления по почте нет.

Для другого Supabase-проекта:

1. Применить `supabase/migrations/*` через SQL Editor или `supabase db push`. Создать две записи Auth через Admin API `createUser({email,password,email_confirm:true})` из доверенного окружения. Идентификаторы фиксированы в `src/lib/api.ts` и защитном триггере `private.guard_account`.
2. Администратором добавить их UUID в `profiles`, слоты 1 и 2. В профилях нельзя зарегистрировать третьего человека. Пользователи не могут менять UUID/слот, вставлять профили или читать данные без членства.
3. В Auth → Providers → Email выключить **Allow new users to sign up**. Дополнительно триггер Auth уже отклоняет любые идентификаторы кроме двух разрешённых; он работает независимо от клиентского интерфейса. Не включать анонимный вход.
4. При утере пароля сменить его через Auth Dashboard/Admin API. Сменить нужно пароль, а не UUID: история привязана к UUID. Не удалять аккаунты.

Миграция не содержит пользователей, паролей или тестовых событий. Первоначальное создание аккаунтов выполнено отдельно. Изменения auth-схемы (триггер допуска) проверить при крупных обновлениях Supabase; не удалять его без отключения регистрации в Auth.

## Данные и безопасность

- RLS на каждой прикладной таблице. Членство по серверной таблице profiles, а не изменяемым JWT user_metadata. Явно отозваны широкие default grants Supabase.
- Названия личных событий вынесены в schedule_details с отдельной RLS; партнёр получает только время/занятость. Тип личного события маскируется сервером.
- Приглашение подтверждает только второй человек. RPC блокирует строку, проверяет версию и допустимый переход. Перекрывающиеся подтверждения сериализуются advisory lock. Прямое UPDATE meetings запрещено. Контрпредложение снова требует ответа.
- Изменение отдельного повторения создаёт новое событие и исключает одну дату исходной серии в одной транзакции. Недельные/чередующиеся недели, выбор дней, ограничение по дате. Удаление дня не удаляет серию.
- Явное свободное время обязательно у обоих. Занятость имеет приоритет; пустые часы неизвестны. Планировщик ищет 90 минут в следующие 7 дней, 08:00–23:00, шаг 15 минут; учитывает дорогу, сборы, буфер возвращения и подтверждённые встречи. Начальное время можно изменить вручную.
- Встречи — `timestamptz`/ISO UTC. Повторяющиеся расписания — локальные даты/часы устройства. Для пары в разных часовых поясах повторения сейчас отображаются в локальном времени каждого; используйте согласованный часовой пояс устройств. Разовые встречи отображаются правильно по локальному часовому поясу.
- Автообновление с сервера каждые 8 секунд, также при возвращении во вкладку. Это polling, не websocket-presence; статуса «партнёр онлайн» нет. Фоновые push-уведомления включаются отдельно на каждом устройстве в настройках профиля.
- Фото до 5 МБ, JPG/PNG/WebP; private bucket, загрузка по JWT с проверкой RLS. Новые фото перед отправкой уменьшаются до 1600 px по длинной стороне и кодируются в WebP, если результат меньше исходного файла. Не используйте публичный bucket. HEIC сначала экспортировать в JPEG. При неудаче сохранения фото удаляется.
- Достижения вычисляются из встреч, подтверждённых совместных сессий, дней истории, знаков внимания, записок и воспоминаний. Место календарной встречи само по себе не запускает совместный таймер: нужно подтверждение обоих.
- Service worker хранит только публичную оболочку/ассеты, не API/фото. Без сети вход и изменения недоступны; очереди offline-изменений нет. Session токен хранится локально для постоянного входа, выходит через Auth logout.

## Обслуживание и деплой

Actions `.github/workflows/pages.yml`: npm ci → тесты → tsc/Vite → deploy Pages. Repository variables `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`. Base `/calendar-duo/`, без history-router: обновление любой вкладки не даёт 404. Для переименования репозитория поменять base в workflow и Vite (manifest и SW используют относительные пути).

`npm run e2e` требует установленного Chromium (`npx playwright install chromium`). Использует реальные два аккаунта из локального игнорируемого файла, создаёт явно помеченные E2E-события. Запускать в отдельном тестовом проекте либо удалить тестовые данные администратором после проверки. В публичном CI паролей нет, auth E2E пропускается. Unit-тесты не используют сеть. SQL проверки доступа/переходов находятся в `supabase/tests/security.sql` и откатываются транзакцией.

Приватные данные и фото не включать в Git. `.env.local`, `.accounts.local.json`, browser traces и test-results игнорируются. Free Supabase может приостанавливать неактивные проекты: восстановить в Dashboard. Экспорт/бэкап данных делать через Supabase перед миграциями. У приложения нет платных API.

## Обновление: квартира и быстрые приглашения

Клик по персонажу выбирает его. Клик по свободному полу отправляет его в точку с обходом мебели. Диван, чайник, телевизор, свет, окно и рабочие столы имеют отдельные области нажатия и доступны с клавиатуры. Реплики следуют за персонажем. Персонажи самостоятельно ходят между занятиями; дискотека и чёрный кот — маленькие развлечения в квартире. Эти движения — локальная виртуальная сцена. Объятия, чай и тычки по-прежнему отправляются партнёру и сохраняются на сервере. reduced-motion отключает автономную ходьбу и анимацию, сохраняя управление.

Приглашение собирается кнопками: день → часы → идея → длительность; произвольное время, место и записка остаются доступны. Аналогично для занятости: тип и кусочек дня, повторения — по желанию.

`./scripts/check-update.sh` собирает production-ассеты, запускает их на порту 5187 и выполняет `e2e/playful.spec.ts` с подменой backend-запросов. Проверяет движение/обход мебели, точные нажатия, привязку реплик, поглаживания кота, приглашения, повторения, reduced-motion и 320 px. **Не изменяет реальные данные пары.** Скриншоты сохраняются в игнорируемой папке test-results. Реальные Auth/Storage-проверки в `e2e/security.spec.ts` запускаются отдельно с локальным файлом аккаунтов.


## Дом, который растёт вместе с вами

Игра занимает всю ширину главной страницы, расписание и приглашения находятся ниже. На телефоне сцена сохраняет крупный масштаб: комната прокручивается горизонтально свайпом или стрелками, а персонажа можно выбрать кнопкой под сценой. Растения и украшения выбираются в горизонтальных каталогах с пиксельными иконками. Управление сохраняет тёплую палитру даже ночью; затемняется сама сцена. Закрытые комнаты можно выбрать и посмотреть под полупрозрачной панелью с условием открытия.

Прогресс зависит от трёх источников: завершённых встреч, подтверждённого времени рядом и дней с вашей даты. За основу берётся наибольшее значение: 100 искр за завершённую встречу, за 90 минут рядом или за 14 дней истории. Источники не складываются. Уже заработанные открытия и рост растений сохраняются. Искры не тратятся. Каждые 300 искр дают новый уровень.

«Мы сейчас вместе» отправляет запрос второму человеку. Он действует 30 минут; отсчёт начинается после подтверждения партнёра. Любой из двоих может закончить совместное время; один запуск ограничен 12 часами. Время считается и с закрытым приложением. На экране прогресс меняется каждую секунду, сервер обновляется каждые 8 секунд. Завершённые календарные встречи и совместные сессии объединяются по интервалам: один и тот же час не считается дважды. Старая отметка профиля на 4 часа больше не запускает рост.

В карточке «Наша история» можно выбрать общую дату начала. Вехи отмечают 7, 30, 100, 180 и 365 дней. Для одинакового результата на обоих устройствах календарные дни прогресса считаются по UTC; день и ночь в комнате по-прежнему следуют местному времени.

| Искры близости | Что открывается |
| --- | --- |
| 0 | Гостиная, семена бархатцев и кактуса, 3 места в саду |
| 100 | Свечи, мята |
| 200 | Спальня, осенняя подушка, семена тыквы |
| 300 | Оранжерея, тыква-фонарь, папоротник, 4-е место в саду |
| 400 | Книги |
| 500 | Привидение, лаванда |
| 600 | Гирлянда с летучими мышами, 5-е место в саду |
| 800 | Монстера |
| 900 | 6-е место в саду |

Декор можно устанавливать и убирать в открытых комнатах. Посадка доступна в оранжерее после 300 искр. Имя растения — 1–24 символа. Виды и вместимость открываются по прежним порогам, выраженным в искрах. Для бархатцев и мяты полный рост занимает 21 день ожидания либо 270 минут рядом после посадки; кактусу, тыкве и папоротнику нужно 28 дней либо 360 минут, лаванде — 35 дней либо 450 минут, монстере — 42 дня либо 540 минут. Календарный рост и совместные минуты складываются; прежние шаги от новых завершённых встреч также сохраняются. Время до посадки не выращивает новое растение. За отсутствие ничего не увядает.

«Слова под подушкой» — общие приватные записки до 1000 символов. Автор видит, прочитал ли партнёр; открыть конверт с отметкой о прочтении может только получатель. Повтор запроса после потери ответа не создаёт дубликат записки или встречи. Последние шесть конвертов видны сразу, остальные — в раскрывающемся списке. Фоновые push для записок в этом обновлении не добавлены.

На полочке 30 достижений в шести коллекциях: история, совместное время, встречи, воспоминания, забота, дом и сад. У каждого есть шкала; текущая встреча учитывается сразу. Новое достижение отмечается сообщением в приложении. Штрафов и обязательных ежедневных серий нет.


День и ночь следуют местным часам устройства: ночь с 19:00 до 07:00. Ручного переключения нет; окно показывает реплику о погоде. За окном осенние деревья и листья, ночью — луна и звёзды.

У персонажей и кошки больше сотни реплик, включая отдельные фразы для чая, объятий, танцев, спальни, учёбы, растений и времени суток. Одинаковые реплики подряд не выбираются. Кошка ворчит, царапает мебель, опрокидывает горшок и ломает декор. Первая пакость возможна через 45 секунд, следующие — раз в 1–2 минуты. «Починить» восстанавливает текущую комнату; повреждения не отнимают прогресс растений и встречи. Во время отсутствия новые повреждения не создаются.

Имена и рост растений, размещение украшений по комнатам, кошачьи повреждения и починки хранятся в одном общем доме на сервере. У обоих участников данные обновляются автоматически каждые 8 секунд, а также сразу при возвращении из фона, восстановлении сети и событии `pageshow`. Ручная перезагрузка не требуется. Текущая комната, выбранный персонаж, движения и открытое меню остаются локальными; переход одного человека в спальню не перемещает второго.

Миграция `20261027190242_shared_home.sql` добавляет приватные `home_state` и `home_operations`, а также RPC `get_home` / `change_home`. Каждая операция содержит уникальный ID; потерянный ответ можно безопасно повторить. Сервер проверяет завершённые встречи, открытие комнаты/вида, имя и свободные места под блокировкой строки. Две одновременные посадки на последнее место не переполняют сад. Ремонт адресует конкретный ID повреждения и не стирает более позднюю пакость. Старые ответы с меньшей ревизией игнорируются.

Пакости создаются по одному общему серверному таймеру при активной доступной комнате. Два клиента не удваивают события; длительное отсутствие сбрасывает ожидание и не создаёт пачку поломок. При неизвестном результате записи интерфейс сохраняет данные операции и предлагает повтор; успешное сохранение не имитируется без ответа сервера.

Если в браузере осталось `ustime.home.v1/v2`, появится «Перенести сохранение с этого устройства». Можно выбрать растения по именам, учитывая свободные места общего сада. Прежние данные не удаляются; неперенесённые растения остаются в локальной копии. Импорт добавляет растения по ID, не заменяет общий снимок, не переносит старые поломки и не восстанавливает убранный декор повторным импортом. Существующие растения, созданные до открытия оранжереи, сохраняются за блокировкой; новые там сажать нельзя.

Демо на входе не читает и не меняет приватный дом. Локальная проверка: `./scripts/check-update.sh`; скрипт запускает сборку и браузерные тесты, ничего не публикует. SQL-проверки общей игры: `psql "$USTIME_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/home.sql` на изолированной базе.

## Push-уведомления на телефоне

Откройте настройки профиля → «Уведомления на телефоне» → «Включить уведомления» и разрешите запрос системы. Затем нажмите «Отправить тестовое уведомление». Приходят приглашения и ответы на встречи, воспоминания и знаки внимания от партнёра. На каждом устройстве включать отдельно. На iPhone/iPad нужна iOS/iPadOS 16.4+ и запуск с иконки на главном экране (Safari → «Поделиться» → «На экран Домой»). Android: браузер с Push API, например Chrome, и разрешение уведомлений. Нужен HTTPS.

Уведомления показываются и при закрытом приложении; нажатие открывает внутреннюю почту UsTime. Системный режим фокусирования и настройки энергосбережения могут влиять на показ. Содержимое уведомления видно на экране блокировки в соответствии с настройками телефона. Это уведомления о действиях партнёра, без напоминаний по таймеру о начале встречи.

Серверное развёртывание:

1. Применить миграцию `20261026205047_web_push.sql` (требуются pg_net и pg_cron).
2. Развернуть `supabase functions deploy web-push --no-verify-jwt`. Функция сама проверяет JWT браузера через Auth и членство в паре. Внутренний dispatcher использует отдельный случайный секрет.
3. При первом открытии настроек функция атомарно создаёт VAPID-ключи и секрет dispatcher в `push_config`. Таблица закрыта RLS и доступна только service_role; браузер получает только публичный ключ. Стандартные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` доступны функции на платформе, дополнительные env/secrets и платные API не нужны. `push_config` не экспортировать в публичные дампы, ключи не менять без перевыпуска подписок на всех устройствах.

Подписки защищены RLS: аккаунт видит и изменяет только свои устройства. Выключение удаляет серверную привязку и browser subscription. Выход сначала отключает подписку на этом устройстве; если сервер недоступен, нужно повторить выход после восстановления связи. В случае выхода из-за истёкшей/отозванной сессии подписка может сохраняться до её отключения в настройках телефона.

Вставка в `notifications` создаёт отдельную доставку для каждой подписки получателя. pg_net вызывает dispatcher после commit; pg_cron повторяет неудачные доставки с задержкой до восьми попыток. Atomic lease защищает от одновременных отправок, стабильный notification tag объединяет повторную доставку на устройстве. 404/410 удаляют устаревшую подписку. Прочитанные и старше 24 часов события не отправляются; транспортная очередь очищается через два дня. Внутренняя история остаётся. Сервер принимает только HTTPS endpoints известных push-сервисов Apple, Google и Mozilla.

Проверки: `npm test`, `npm run build`, `supabase/tests/push.sql` (RLS, недоступность ключей/очереди, lease, retry, unsubscribe; транзакция откатывается). Проверка настоящего системного уведомления на физическом телефоне выполняется тестовой кнопкой после разрешения.


### Напоминания о встречах

Серверная миграция `20261027155637_meeting_reminders.sql` добавляет проверку раз в 5 минут через [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart). Обоим участникам приходят уведомления внутри сайта и, при включённой подписке, push через существующую очередь:

- перед подтверждённой встречей, когда до начала остаётся не больше часа;
- однократно, если подтверждённая встреча не завершена через 12 часов после начала;
- после 14 дней без состоявшихся встреч, не чаще раза в неделю, с 09:00 до 21:00 по Минску. Уже запланированная подтверждённая встреча подавляет это напоминание. Если история пуста, отсчёт начинается с создания второго аккаунта.

Приватный журнал исключает повторную отправку при повторных запусках и пересечении задач. Отмена/перенос/завершение встречи снимают старые сообщения из очереди повторной доставки. Напоминание «перед встречей» также перестаёт повторяться после начала. Пропущенные еженедельные напоминания не отправляются пачкой после простоя.

Миграция применена на сервере 27 октября 2026 года; новые напоминания активны. Она зависит от миграции `web_push`. Для проверки на PostgreSQL под администратором: `psql "$USTIME_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/reminders.sql`. Тест откатывает все данные; локальная проверка использовала настоящие таблицы/функции и заглушки только для cron-регистрации и HTTP-отправки. GitHub Pages и рабочая база при этой проверке не меняются.

Миграция `supabase/migrations/20261031150834_living_story.sql` применена к рабочей базе `ustime` 31 октября 2026 года. GitHub Pages при этом не публиковался. Пока миграция не применена, календарь и дом работают, а новые действия показывают карточку ожидания обновления. Для применения используйте отдельную тестовую базу; публикация сайта и применение к рабочей базе выполняются отдельно.

Проверки: `npm test`, `npm run build`, `./scripts/check-update.sh` (mock API, без реальных аккаунтов). `supabase/tests/story.sql` проверяет права, подтверждение вторым человеком, повторы операций, объединение времени и живой рост. Его нужно запускать администратором на изолированной базе с применёнными миграциями и пустыми профилями; тестовые пользователи и данные откатываются транзакцией. `supabase/tests/home.sql` проверяет совместимость прежнего дома на тестовой базе с двумя профилями.

## Быстрая загрузка фотографий в истории

Фотографии загружаются одним авторизованным запросом без отдельного запроса временной ссылки. Подгрузка начинается за 400 px до появления карточки на экране; одновременно скачиваются максимум 3 фото. Одинаковые запросы объединяются. Повторное открытие истории использует кеш Blob в памяти вкладки: 15 минут, до 24 МиБ и 32 снимков, с вытеснением давно не открывавшихся фото. Выход или смена аккаунта очищают кеш и отменяют незавершённые загрузки. На диск, в localStorage, IndexedDB и service worker фотографии не записываются; после перезагрузки страницы понадобится новая загрузка. Сбой сети показывает кнопку «Загрузить снова».

Новые фотографии сжимаются на устройстве до отправки (WebP, качество 0.82, до 1600 px по длинной стороне). Если перекодирование увеличивает размер, отправляется исходный файл. Прозрачность сохраняется. Уже сохранённые оригиналы не меняются. Загруженный снимок сразу доступен из кеша без повторного скачивания. Тесты `e2e/photos.spec.ts` проверяют отложенную загрузку, повторную навигацию, восстановление после ошибки и сжатие реального изображения через Canvas; включены в `./scripts/check-update.sh`.
